# Development and debugging roadmap

1. **Completed: establish scope and audit.** Pin original V48 source commit and hashes, distinguish later V52/PlayerCamera descendants, identify native ABI and coordinate boundaries. No Free Fire MAX compatibility or hit authority is inferred.
2. **Completed: implement minimal owned scene.** Six known sphere hurtboxes, server-owned origin, finite hitscan, wall and analytic geometry tests. Keep both physical region and awarded classification.
3. **Completed: external application and server.** Independent C# console client, loopback HTTP contract, server policy selection at startup, issued sessions/sequence checking, bounded requests, browser test game.
4. **Completed on Linux: verify experiments.** Run actual HTTP tests and separate server/client processes, record geometric/convert/wall outputs, RTT and client/server disagreements. Review evidence for exact counts. Neither Linux build success nor source-level V48 compilation proves native Windows/COM behavior.
5. **Pending on user's Windows 11: platform acceptance.** Install .NET 8 x64, run `environment`, `test`, server and client as documented. Check browser clicks and HTTP listener permissions. Preserve Windows outputs. This can be done without Free Fire or BlueStacks running.
6. **Optional controlled expansion: animated engine.** Replace browser mannequin with a Unity/other owned client. Expose explicit scene/tick and skeleton/hurtbox contracts from its server. Reuse server collision policy and reporting interfaces; use known coordinate transforms and controlled test cases before adding moving players.
7. **Optional controlled expansion: realism.** Add persistent health and weapons, fixed server ticks, server-owned firing cadence/ammo and muzzle pose, network impairment tests, replayable snapshots, explicit rewind and projectile sweeps. Quantify numerical error and false accept/reject rates against an independent oracle.
8. **Commercial-title conclusions remain blocked by evidence.** A Free Fire MAX claim requires authorized access to authoritative implementation/test infrastructure or equivalent documented evidence. A client-side memory observation or custom DLL does not supply this. This local experiment neither implements nor predicts a server bypass.

Debug geometry before networking, then compare a serialized shot with `Authority.Submit` and its HTTP receipt. If a test unexpectedly returns Head, inspect `GeometricRegion` and configured policy first. If a client says Head but receipt says Chest, the authority boundary is functioning. If convert accepts a miss/wall/replay, that is a lab bug and tests must fail.
